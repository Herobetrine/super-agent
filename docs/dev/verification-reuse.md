# 验证复用与工作区效率

本文对应[长期设计](../architecture-evolution.md) §10 和 P3。目标是减少重复检查和串行等待，同时不漏检。

## 检查复用的验证键

完成检查只有在以下两项都一致时才复用已通过的结果：

- 工作树指纹：HEAD、状态、差异，以及未被忽略的未跟踪文件内容。
- 验证键（`verification-key/1`），见 [verification.rs](../../crates/sa-engine/src/verification.rs)。

验证键包含：

- 检查命令行。
- 平台（OS 与架构）。
- 每个命令所解析到的程序身份：路径摘要、大小、修改时间。
- `PATH` 的摘要。
- 一组影响构建的环境变量的摘要：`RUSTFLAGS`、`CC`、`NODE_ENV`、`PYTHONPATH`、`JAVA_HOME`、`GOFLAGS` 等。

回执只保存摘要，不保存变量值。键记录在完成检查回执的 `verification_key` 中。升级后，旧缓存因键不同会重新检查一次。

验证键不覆盖网络、时钟、数据库、工作树外文件和被忽略的文件。依赖这些输入的检查，复用行为与验证键引入前相同。这是已知限制。

## 交付证据不再依赖项目检查

以前只有配置了项目完成检查，才会自动核对交付证据。现在只要工单有已采用的行为检查或文件摘要需求，写入任务声明完成时也会捕获快照并核对。没有项目命令时，回执的 `runs` 为空。

交付门开启时，即使本轮工作树没有变化，也会为必需项取得证据（§10.2）：

- 项目命令不重跑，回执标注 `unchanged`。
- 交付证据在快照上核对。
- 同一输入、合同和门策略已有核验、且行为检查都已有终态结果时，不再重复核对，也不新增核验回执。

## 合入候选只检查一次

开启合入队列时，以前要检查两次：

1. 在隔离工作区里执行全部项目检查。
2. 在合并候选里再执行一次。

现在先判断原项目的当前提交是否仍是任务分支的祖先。如果是，候选合并后的内容树与任务相同，检查只在干净的候选目录里执行一次。验证回执的 `workspace_checks` 记为 `{"reused_from":"candidate_checks","tree":…}`。

候选目录不含任务工作区里被忽略的文件，所以这是较严格的那次检查。如果原项目已有新提交，或合并后内容树意外不同，仍按原流程先检查任务工作区。

用户确认不复用：每次重新验证都生成新的确认令牌。

## 共享前置的短租约

依赖多个前置写任务的隔离写任务，会从前置分支合并出自己的快照（§10.1）：

- 以前，后继在整轮执行期间都占用前置工作区，共享同一前置的后继只能串行。
- 现在，前置工作区只在后继准备快照时占用（提交检查点、核对版本、合并）。准备完成后释放，其他后继可以并行开始。
- 已经建好快照的后继在后续轮次不再读取前置，也不再占用它们，而是继续使用自己的版本。前置之后再被续派，会产生新版本，不影响已开始的后继。

## 依赖下载缓存

平台没有为隔离工作区另设构建目录，各工作区的构建产物互相独立，也不共享可变的构建目录。包管理器的下载缓存默认按用户全局共享，例如 `CARGO_HOME` 和 npm cache，平台不改动它们。

## 回归

```powershell
scripts\cargo.cmd test -p sa-engine --test verification_reuse --test integration_queue --test completion_checks -- --test-threads=2
```

覆盖以下场景：

- 同一工作树换了检查程序后不再复用。
- 没有项目检查时核对交付证据。
- 交付门开启、工作树未变时只取一次证据。
- 候选内容树相同时只检查一次。
- 共享前置的第二个后继在第一个仍运行时开始。
