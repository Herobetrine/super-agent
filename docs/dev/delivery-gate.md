# 可选快照交付门

这是[长期架构设计](../architecture-evolution.md) P1A 的显式快照交付门，接续[第一轮需求证据](delivery-evidence.md)。下文记录最初的文件标准流程。2026-11-18 起，门也核对需求采用的行为标准，并将每次评估绑定到当时的行为检查回执。[在快照上验证行为](delivery-behavior.md)

## 使用流程

入口仍是 **项目面板 → 协作 → 需求与交付证据**。

1. 记录需求和事先确定的文件标准，捕获列出的交付文件。
2. 显式启用“快照交付核验”。默认关闭，旧工单不会自动开启。现有未撤销需求默认必需，纯文字需求仍没有自动通过证据。
3. 按实际约定调整必需状态。操作员可将某项改为可选、撤销或恢复，并填写理由。每次调整都增加需求合同版本，历史记录保留；模型没有自动降低要求的入口。
4. 对当前合同重新捕获文件后，点击“核验快照交付”。平台核验冻结对象、需求版本和采用范围，保存可追溯的结果。
5. 如有未满足项，查看对应原因并补充产物或调整明确的需求约定。该操作不会自动发起模型重试，也不会停止持续任务。

只读窗口可以查看和刷新，不能更改策略、需求状态或提交核验。普通需求编辑会保留已采用的必需/可选/撤销状态，不会悄悄恢复默认范围。

需求编辑器和必需状态编辑器都固定打开时的合同版本。编辑途中刷新发现别人已修订时，会保留草稿、提示冲突并禁用保存；重新打开对应编辑器才载入新版本。刷新不会替旧草稿自动换上新版本号。

## 两类结果分别展示

| 项目 | 含义 | 后续变化 |
| --- | --- | --- |
| 快照文件标准符合 | 指定快照的所有有效必需项都具有文件摘要通过证据，且至少存在一个必需项 | 需求合同、门策略或最新快照改变后，旧核验变过期；对象缺失或损坏则重新计算为受阻或部分符合 |
| 部分符合 | 至少一个必需项通过，仍有必需项失败或未知 | 列出当前未满足项；不自动修复或重试 |
| 交付受阻 | 没有可通过的必需项，或无法核验交付依据 | 纯文字需求未知、全部需求可选/撤销、缺失对象都不能凭空得到通过结论 |
| 当前项目文件证据 | 最近一次读取当前项目文件与快照的对应关系 | 当前文件修改后会过期，与历史快照标准的结果独立 |
| 用户接受 | 本轮没有新增人工接受记录功能 | 快照标准通过不代表用户接受 |

例如，快照 #2 的文件符合标准，之后 agent 修改了项目文件。此时“快照 #2 标准符合”和“当前项目文件证据过期”可以同时成立：前者说明保留的交付字节，后者提醒当前文件已有变化。没有自动推导当前代码已合入、测试通过或发布。

## 版本和并发约束

需求范围、门策略和核验回执分别追加保存。核验绑定工单、需求合同版本、策略版本、快照编号和清单 SHA-256。策略关闭再开启仍产生新版本，不能让之前的通过记录直接恢复为当前核验。

核验在数据库写事务之外读取冻结对象，保存时再次比较合同、策略、最新快照及清单摘要。期间这些依据变化，旧界面的请求报“刷新后重试”，不把旧结果写到新版本。读侧再次核验对象并重算当前标准结果，不把保存的 `ready` 字符串当作有效证据。历史回执与当前重算结果分开保存和显示。

如果旧核验因对象缺失或损坏未通过，修复对象后显示“需要重新核验”，由操作员重新提交形成新回执；不悄悄把历史失败改写为成功。损坏或超限的历史未满足项记录会降级显示，仍可修订、关闭门或提交新的核验。

历史核验字段出现 BLOB、无效文本或数值类型损坏时，也按无效记录处理，不阻断合法的需求编辑。策略字段损坏时门关闭；版本号仍可信时可显式保存下一版设置恢复。如果策略版本号本身损坏，系统无法可靠恢复修订顺序，会要求维护策略记录，需求编辑仍可用。这不是任意 SQLite 损坏的自动修复工具。

该门不宣称提交瞬间整个工作区内容一致，也不为核验冻结整个仓库。当前文件读取仍是有界的逐文件核对，适用第一轮的路径、体积和链接限制。交付快照不因之后修改项目文件而变化。

旧快照缺少新增范围字段时解释为必需且未撤销；旧工单门仍默认关闭。旧账本只读查看不会创建新表。三个附加表保存需求状态、门策略和核验记录，原有 job 状态机及持续运行规则保持独立。

## 开发与复验

核心入口在 `sa_engine::Engine`：

```rust
set_delivery_gate(ticket, expected_policy_revision, enabled)
set_requirement_disposition(ticket, expected_contract_revision,
                            requirement_id, required, withdrawn, reason)
prepare_delivery(ticket, expected_contract_revision,
                 expected_snapshot_id, expected_policy_revision)
```

复验使用项目 Cargo 包装器，运行两层 `delivery` 测试、引擎 `delivery_gate` 测试及桌面 `delivery_` 测试，再执行工作区构建、全量测试和 Clippy。

原生界面的合成样本可用以下命令创建。目标目录必须为不存在的绝对路径，其父目录应已存在；程序拒绝复用现有目录，不调用模型、不启动调度器。

```powershell
scripts\cargo.cmd run -p sa-engine --example delivery_gate_demo -- C:/path/to/new-fixture
target\release\super-agent.exe --data C:/path/to/new-fixture/ledger --observe --ticket 1 --inspector collab --expand-all
```

样本通过实际交付 API 核对：默认关闭、必需项未知阻塞、操作员改为可选、合同变更失效、重新捕获和核验、修改当前文件后历史快照仍符合，以及重新只读打开。它生成 `receipt.json`，不构成真实业务或人工体验验收。

本轮不包含自动需求提取、行为/界面验证器、基于任务报告自动提交交付、人工接受操作、调度策略选择和仓库原子快照。具体执行结果与发布版本见[验证记录](../verification.md)。
