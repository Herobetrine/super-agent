# 正常工单的用量观察与交接暂停

使用正常工单采样，不为测试额外调用模型。界面输入区的 **交接后暂停** 会保留当前操作，等待已有协作者完成，必要时允许一次主控汇总交接，再阻止该工单后续轮次。最终汇总轮不能再派新任务。已经停止的工单可直接进入暂停，不新增模型调用。

暂停门与任务的成功、失败、取消状态分开保存。重启仍然暂停；追加留言、重试任务不会自动解除暂停。点击 **恢复调度** 明确解除；正在等待交接时可点击 **取消暂停请求**。原有立即停止按钮仍按原行为取消任务。需要操作员审批或执行端没有结束时，交接也会等待，不声称能够保证固定时限内停下。

## 本机控制接口

锁定工单库的工作台提供同用户文件接口，目录为数据目录下的 `control/`，没有网络监听。请求只允许查询状态、交接后暂停和恢复，不接受代码、路径或模型提示。请求通过原工作台的 Engine 执行；测试脚本不直接修改数据库，也不启动第二个调度器。目录访问遵循本机用户文件权限，不是面向不可信用户的服务。

```powershell
$data = "$env:USERPROFILE/.local/share/superagent/control-room"
python scripts/agent-control.py --data $data status --ticket 6
python scripts/agent-control.py --data $data pause-after-handoff --ticket 6
python scripts/agent-control.py --data $data resume --ticket 6
```

返回状态 `draining` / `handoff` 仅表示暂停请求已受理；只有 `paused` 才表示后续调度已经暂停。应继续观察正在运行的任务数与交接回执。接口有版本与当前进程代号，旧进程遗留的请求不会在重启后恢复调度。

## 只读采样

```powershell
python scripts/watch-agent-run.py --database "$data/hub.sqlite3" --ticket 6 `
  --after-seq <开始前事件序号> --output <新的JSONL路径> --duration 900
python -m unittest discover -s scripts -p test_watch_agent_run.py
```

从指定事件游标增量读取，每批有上限，默认每 5 秒取一次；不导出提示、工具参数、回复正文或凭据。输出 JSONL 及摘要，保留原始工单日志作为交接与任务质量证据。使用新文件路径，避免混淆不同观察窗口。

比较指标包括主控与员工的轮次、全量/增量输入字节、原生 Token、缓存读取与写入、重试、压缩、等待时间与完成状态。Claude 请求样本和终态合计是两种重叠视图，不能相加。缺失字段不当成 0，输入字节不当成 Token 或账单；原生内部子任务与未报告用量仍可能缺失。

不要用冷启动的一次低缓存率触发结论。观察后续同会话复用是否仍重复全量注入、是否反复压缩或重试，以及调用是否推动任务完成。出现持续退化后请求交接暂停，核验 `paused` 与实际交接，再修改实现并用离线回放验证。99% 是优化目标，不能通过付费保温或增加冗余上下文追求指标。

暂停设计参考了 [LangGraph 持久化中断](https://docs.langchain.com/oss/python/langgraph/interrupts)的保存状态和显式恢复原则；实现复用本项目 SQLite 事务与调度锁，没有引入新的 agent 框架。

## 验证边界

2026-11-10 的全量 Rust 回归报告 388 passed / 0 failed / 3 ignored，Clippy `-D warnings` 通过；环境门控测试的提前返回不等于真实模型验证。7 项暂停专项使用假执行端，覆盖保留活动操作、等待员工、一轮交接、禁止新派工、重启、失败及有限重试。恢复说明修补后，7 项专项再次通过。真实 App 点击回归覆盖暂停、追加指令仍排队和显式恢复。

本机接口测试覆盖旧进程代号拒绝、重复请求、畸形请求、临时文件干扰，以及操作已成功但回执发布失败时不重复执行旧恢复命令。Python 采样器 6 项离线测试验证样本去重、工单隔离、脱敏、用量口径与结束计时。实际工单的缓存效果、Token 成本与交接质量需另行观察，不能由这些离线检查推断。

## 首次正常续跑发现的兼容问题

一次正常工单续跑在实际工作开始前连续两轮返回 `API Error: 400 Per-turn system messages require upstream per-turn-control support`。两轮平台投递合计 746,457 字节，原生终态都报告 Token 为 0；这是失败样本，不能据此计算缓存命中率或确认供应商账单。工单停止后设置了持久暂停门，保留原会话。

确认了两个问题并修复：

- 原生 `result` 同时为 `subtype=success`、`is_error=true`，随后进程退出码为 1。此前通用进程崩溃路径覆盖了明确的 API 错误，引发重试；现在声明失败的终态可将通用退出错误细化为 HTTP 400 / `Protocol`，重试预算为 0。成功回复中提到错误不会触发此判断。
- 已绑定本地网关的模型能力兼容项只写在子进程环境里，被用户 `settings.env` 中的能力列表覆盖。现在只为现有绑定路径，通过本轮 `--settings` 传入合并后的 `CLAUDE_CODE_MODEL_CAPABILITIES`，保留其他模型及能力项；不修改全局设置、凭据或网关。受限模式继续不加载用户/项目配置，managed 设置仍有更高优先级。[Claude 设置优先级](https://code.claude.com/docs/en/settings#settings-precedence)

使用实际 Claude Code 2.1.317 对隔离回环假服务复现，进程变量方案的请求角色为 `user,system`，本轮设置方案为 `user`；同一会话恢复后为 `user,assistant,user`。每次只有一个本地假响应请求，不访问实际网关或模型。追加的 5 项适配器回归验证能力设置优先级、限定字段、错误配置、终态错误分类和传输错误优先级；采样器增加失败标记与暂停门读取回归，合计 7 项。真实工单修复后的恢复、长期 Token 和缓存效果仍需正常工作负载验证。

修复后的全量回归为 394 passed / 0 failed / 3 ignored。暂停专项增加已完成、已取消和失败主控的恢复，合计 8 项：恢复门不改变终态、不向停止收信的任务投信，撤销说明在下次正常续轮读取。未知原生错误保留既有进程退出重试分类，只对已确认的错误分类细化。

## 新工单首轮观察

2026-11-13 的新工单完成首轮并在交接边界进入 `paused`，下一轮可处于 `queued`，但暂停门阻止准入；应区分排队与实际运行。网关观察到成功请求，首包仍因大型 MCP 目录占 80.83% 而产生较高装载开销，见 [按需参数读取](token-efficiency.md#大型-mcp-目录按需读取)。原生 `compacting` 状态可能重复，不能将每条状态当成一次完成的压缩；原生主循环合计和网关全部请求（可能含压缩请求）也不能相加。

同轮的 `SA_SEND` 因把尚未创建的输出文件填入 `files` 而失败。`files` 是现存输入附件快照，不是输出清单或写入范围。现在 guide 明确区分，错误信息给出缺失的相对路径并提示将未来输出路径写入 `body`。缺失附件仍拒绝；不会创建占位文件或把缺失附件伪装成成功快照。恢复时必须核对实际子任务和 `send` 回执，不以主控文本中的“已派出”为准。
