# 协作闭环后续开发

本轮接续三项：自动合入队列、推荐完成检查，以及依据真实验收结果收紧固定引导。真实模型与自动验证的证据分别记录，任务 `done` 不等于代码已经合入。

## 操作入口

在项目面板的「协作 → 完成检查」中查看推荐命令及来源。读取 `Cargo.toml`、`package.json` 和锁文件只产生建议；点击「采用推荐检查」才会保存并启用。原有检查保留、相同命令去重，总数最多四条；也可以手工添加或移除后保存。只读窗口不出现采用按钮。

Cargo 推荐工作区测试和构建；Windows 项目若存在 `scripts/cargo.ps1`，沿用其相对路径。JavaScript 项目按 `packageManager` 或锁文件选择 npm、pnpm、yarn，仅推荐实际声明的 test、lint、build 脚本，跳过 npm 默认占位测试。管理器冲突、坏清单或无法识别的情况显示原因。识别阶段不运行脚本、不安装依赖，也不保证建议覆盖全部业务规则。

在「隔离工作区与合入」启用隔离写入、保存完成检查，再勾选「自动验证合入队列，合入前由我确认」。队列只处理隔离写入任务：保存任务分支提交，在任务工作区运行检查，再用独立候选工作区合并并复验。通过后停在「待你确认」。核对候选、检查输出及提交后点击确认，才会更新原项目的本地分支。不会推送到远端。

验证失败或合并冲突时，平台将失败输出和候选信息退回原任务，沿用原会话修复，合入队列自动退回最多两次，与任务完成检查自身的退回计数分别记录。超过上限或出现基础设施问题时停止并显示原因；处理后可重新排队验证。停止工单或关闭程序会取消运行中的队列检查。显式停止工单会同时关闭该工单的队列开关，恢复后需要重新开启；单纯关闭程序会保留待重验状态。

## 版本和持久化边界

队列默认关闭，策略与队列项持久化。重新启动后中断的验证需要重跑。确认绑定本次验证回执及界面展示的候选提交，并重新核对任务版本、检查命令、任务分支、原项目和候选状态；即使重新验证得到相同提交，也不能沿用旧确认。原项目有未提交修改时不会强制清理或覆盖。确认一个候选后，同源其他待确认候选自动重新排队验证。

后续隔离写任务可以依赖已经完成的前置工作区。构建基线时核对前置版本，不依赖模型复制文件或自行合入原项目。共享同一前置工作区的写任务当前会串行执行，避免前置续派与依赖准备互相覆盖；没有共享前置的隔离写任务仍可并行。不同前置分支产生冲突时保留现场并报告；不会替操作者猜测冲突的业务含义。

实现复用原有目录租约、进程树取消、Git 工作区和项目检查机制，未引入新依赖。[Git worktree](https://git-scm.com/docs/git-worktree) 支持指定提交创建独立候选；确认使用 [Git merge 的 `--ff-only`](https://git-scm.com/docs/git-merge) 发布已验证提交，无法快进时拒绝。开发环境 Git 为 `2.55.0.windows.2`。
