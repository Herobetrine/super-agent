# 协作闭环后续开发

本轮接续三项：自动合入队列、推荐完成检查，以及依据真实验收结果收紧固定引导。真实模型与自动验证的证据分别记录，任务 `done` 不等于代码已经合入。

## 操作入口

在项目面板的「协作 → 完成检查」中查看推荐命令及来源。读取 `Cargo.toml`、`package.json` 和锁文件只产生建议；点击「采用推荐检查」才会保存并启用。原有检查保留、相同命令去重，总数最多四条；也可以手工添加或移除后保存。只读窗口不出现采用按钮。

Cargo 推荐工作区测试和构建；Windows 项目若存在 `scripts/cargo.ps1`，沿用其相对路径。JavaScript 项目按 `packageManager` 或锁文件选择 npm、pnpm、yarn，仅推荐实际声明的 test、lint、build 脚本，跳过 npm 默认占位测试。管理器冲突、坏清单或无法识别的情况显示原因。识别阶段不运行脚本、不安装依赖，也不保证建议覆盖全部业务规则。

在「隔离工作区与合入」启用隔离写入、保存完成检查，再勾选「自动验证合入队列，合入前由我确认」。队列只处理隔离写入任务：保存任务分支提交，在任务工作区运行检查，再用独立候选工作区合并并复验。通过后停在「待你确认」。核对候选、检查输出及提交后点击确认，才会更新原项目的本地分支。不会推送到远端。

验证失败或合并冲突时，平台将失败输出和候选信息退回原任务，沿用原会话修复，合入队列自动退回最多两次，与任务完成检查自身的退回计数分别记录。超过上限或出现基础设施问题时停止并显示原因；处理后可重新排队验证。停止工单或关闭程序会取消运行中的队列检查。显式停止工单会同时关闭该工单的队列开关，恢复后需要重新开启；单纯关闭程序会保留待重验状态。

### 补齐被忽略的生成资源

`git worktree` 只带出 Git 跟踪的文件。有些项目的构建和运行依赖被忽略的生成资源（导出的模型、动作、第三方工具），隔离工作区和合并候选里缺了它们，就没法构建或启动客户端。

在「隔离工作区与合入」的「补齐的忽略资源」里，按每行一个填写项目内的相对路径，保存后对该项目所有工单生效。也可以调用 `Engine::set_workspace_hydration`。规则如下：

- 时机：创建任务工作区和每个合并候选时，用 `git ls-files --others --ignored --exclude-standard` 列出这些路径下被忽略的文件，再从原项目复制进去。Git 跟踪的文件仍由 Git 提供，不在复制范围内。
- 上限：最多 32 条路径。总量超过 20 万个文件或 8 GiB 时，整次拒绝，不会只复制一部分，需要缩小路径。
- 路径限制：不接受绝对路径、`..` 或 `.git`。
- 回执：工作区的 `validation.hydration` 和候选的 `validation.candidate_hydration` 记录文件数、字节数和本次实际复制数。崩溃后重做时，大小相同且不旧于原文件的文件会跳过。
- 限制：任务对补齐文件所做的修改留在它自己的工作区，**不会合入**原项目。需要交付的生成资源必须由 Git 跟踪，或者由合入后的构建重新生成。

### 原项目忙时确认

主控本身在原项目里写入，运行时会占用原项目目录。此时点确认不会报错：候选会记为「已确认，等待空闲后合入」（`confirmed`），由调度器在主控两轮之间完成合入，合入期间主控先排队。发布前仍会核对候选是否有效；原项目在此期间有新提交时，按原规则转为过期并重新验证。程序重启后，`confirmed` 会退回「待你确认」，需要重新确认。

### 确认沿用到新基线

确认针对的是**任务版本**，也就是任务工作区的提交和任务轮次，不是某一个合并候选。规则如下：

- 确认后发布时发现原项目有新提交：这次不会合入任何东西，候选会自动回队列，基于新的原项目重新验证。任务版本没变，并且新候选重新通过全部检查时，沿用之前的确认，直接进入「已确认，等待空闲后合入」，不再请操作员重复确认。
- 任务版本改变时（续派、自动修复、重新派工），确认作废。
- 因其他原因被拒时（原项目有未提交修改、项目检查改变、结果未知），确认作废。
- 操作员手动「重新验证」时，确认作废。
- 程序重启后，确认作废。

这样可以避免主控每轮往原项目提交、候选反复等待确认的循环（[P45 记录](../verification.md#真实大型项目工单mc-genshin-p452026-11-19)）。代价是：原项目新增的提交与任务合并后的结果，只经过自动检查，不再经过人工复核。

### 工作区清理

- 合入记录写入后，平台删除该任务的合并候选和任务工作区。合入后的任务不能续派，所以不再需要它的工作区。
- 每次为同一任务准备新候选前，先删除它之前的候选。
- 清理只针对数据目录下 `workspaces/` 和 `integrations/` 中平台创建的目录，用 `git worktree remove`；失败时保留目录，不影响合入结果。
- 任务分支不删除。

### 平台提交说明

平台生成的检查点与合并提交不再使用笼统文字。主题不超过 72 个字符，按字符边界截断：

- 检查点：`Checkpoint task #<任务> (ticket <工单>): <标题>`
- 合入候选：`Merge task #<任务> (ticket <工单>): <标题>`
- 前置分支：`Merge prerequisite task #<前置> into task #<依赖方>`

标题取任务正文的第一行，去掉控制字符并截到约 60 个字符，不含完整提示词或多段目标。正文记录工单、任务、轮次和分支名。工作区读取时附带该描述（`Workspace.label`，不落库）；没有任务信息时检查点仍用旧文字 `Checkpoint isolated Super Agent task`。操作恢复只比较提交祖先关系，不依赖提交说明，新旧文字都能对账。

## 版本和持久化边界

队列默认关闭，策略与队列项持久化。重新启动后中断的验证需要重跑。确认绑定本次验证回执及界面展示的候选提交，并重新核对任务版本、检查命令、任务分支、原项目和候选状态；即使重新验证得到相同提交，也不能沿用旧确认。原项目有未提交修改时不会强制清理或覆盖。确认一个候选后，同源其他待确认候选自动重新排队验证。

后续隔离写任务可以依赖已经完成的前置工作区。构建基线时核对前置版本，不依赖模型复制文件或自行合入原项目。共享同一前置工作区的写任务当前会串行执行，避免前置续派与依赖准备互相覆盖；没有共享前置的隔离写任务仍可并行。不同前置分支产生冲突时保留现场并报告；不会替操作者猜测冲突的业务含义。

实现复用原有目录租约、进程树取消、Git 工作区和项目检查机制，未引入新依赖。[Git worktree](https://git-scm.com/docs/git-worktree) 支持指定提交创建独立候选；确认使用 [Git merge 的 `--ff-only`](https://git-scm.com/docs/git-merge) 发布已验证提交，无法快进时拒绝。开发环境 Git 为 `2.55.0.windows.2`。
