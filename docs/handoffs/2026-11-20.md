## 3. 自 2026-11-18 交接以来的核心进展

### 3.1 架构演进 P0A–P5 全部落地并进入 `main`

- **P0A（计量与基线）**：顾问独立计量、逐次执行用量账目（`execution` 维度拆分同轮中断与重试，避免覆盖少计）、缺口原因码、真实库副本只读现状报告。
- **P0B & P1A（需求合同、证据与交付门）**：版本化需求修订、产物快照、行为检查绑定快照、完成时自动核对、交付门与操作员显式接受。
- **P1B（上下文选择）**：按角色内容包、压缩保留必需需求项、名册裁剪、项目知识依赖文件记录与过期/取代机制。
- **P2（执行策略 `rules-1`）**：派工/重试/修复三决策点，支持 `record`（默认）与 `apply` 两模式，按不同轮次计恢复预算、同类失败 3 次重诊断、重叠隔离写排队、桌面端开关与决策记录。
- **P3（验证与工作区效率）**：环境感知验证缓存、候选单次检查、共享前置短租约、忽略生成资源自动补齐（`hydrate`）、合入/取代后自动清理工作区。
- **P4（操作恢复）**：平台发起的 Git / 合入 / 行为检查 / MCP 操作留回执、重启对账不盲目重做、未知效果由操作员在桌面端确认、取消区分请求与确认。
- **P5（固定任务集与受控试验）**：`eval/suites/core-v1`（1.1.0）六类任务 + `trial` 对照执行器。

### 3.2 受控试验与大型实战压测暴露的问题及修复（已提交至 `main`）

1. **Opus 5.5 `core-v1` 受控试验（`69874a4`）**：36 次有效运行隐藏验收 36/36 通过、0 返工；修复了试验执行器不重试中断任务、重启时机过晚、以及账目合并同轮重试导致少计 28% 输入 Token 的缺陷。因单执行者均独自一轮完成，未触发派工与策略差异。
2. **`mc-genshin` P41（5.3 小时，25 任务，无隔离）与 P45（首次全开隔离写入 + 资源补齐 + 合入队列 + 统一完成检查）**：
   - 验证了多写入者隔离并行（P45 最多同时 3 写入者）、合入检查失败自动退回修复、以及任务/候选验证复用。
   - 将两轮实战暴露的缺口全部补齐并合入 `8a4374c`：
     - **建单路由校验**：`Engine::create` 对照实时模型目录校验明确路由，缺失模型或未声明思考强度即拒绝建单。
     - **目录 12 小时缓存 + 短暂探测失败可重试**：`catalog::fetch` 记住最近成功目录（12h 内拉取超时/503 沿用），已配置路由偶发探测缺失改判可重试，不再直接永久失败。
     - **忽略生成资源补齐**：新增 `crates/sa-engine/src/workspaces/hydrate.rs` 与桌面端/引擎配置接口，隔离工作区和合并候选自动复制指定路径下被 `.gitignore` 忽略的构建资源（不回写合入）。
     - **确认沿用（解决 P45 确认活锁）**：确认绑定任务代码版本（工作区提交 + 轮次），原项目前进触发自动重验通过后沿用确认；任务版本变化、手动重验或重启仍作废。
     - **工作区与候选自动清理（解决 E 盘写满）**：合入落盘后自动移除对应合并候选和任务工作区；准备新候选前先清旧候选。
     - **其余修复**：共用目录 `partial` 前置不再跳过下游；非隔离写入统一建议 `serialize`；向主控暴露 `harness_capabilities.readonly_commands`；本机控制接口补齐 `answer` / `decide` / `retry` / `follow` / `stop` / `confirm`（同步返回）/ `revalidate`。
3. **桌面端窗口坍塌兜底（`e3bc0b3`）**：
   - 现场发现 `eframe` 在 `%APPDATA%/super-agent/data/app.ron` 中可能把最小化/异常关闭的窗口存成 `inner_size_points: (1712.0, 64.0)`，导致再次启动缩成邮票大小。
   - 已在 `main.rs` 增加启动前 `app.ron` 坏 `"window"` 条目自动清洗，并在 `app.rs` 首帧增加低于 `880×600` 的运行时重置兜底（新增 3 项单测）。

## 4. 六项原始需求的真实完成度与缺口

| 原始目标 | 机制完成度 | 实证 / 验收程度 | 当前结论与核心缺口 |
| --- | --- | --- | --- |
| **1. 协作效率更高** | ~85% | ~45% | 并行隔离写、依赖/续派、资源补齐、验证复用、确认沿用、自动清理均已落地；P45 实测跑出多写并行与验证复用。**缺口**：确认沿用与自动清理尚未跑完一整单全链路；缺少与旧架构同任务的定量提速/返工对照。 |
| **2. 交互体验更舒适** | ~75% | ~25% | 待你处理聚合、交付卡片、策略/账目/操作核对面板、交接后暂停、窗口防折叠均已实现，自动 UI 测试 141 项全过。**缺口**：**尚未进行用户本人桌面端体验验收**；旧大库冷读（~20s）与 Windows 通知点击导航未优化/验收。 |
| **3. Agent 功能更全面** | ~85% | ~65% | 四端 + ACP、MCP、技能、图片、知识库、自动 Git、合入队列、顾问、本机控制均就绪，代码工程多端协作已跑通。**缺口**：非代码任务和四端全混对照尚未实测覆盖。 |
| **4. 多数情况下更自主** | ~90% | ~75% | **实证最充分**：`core-v1` 36/36 零纠错救场（含 6 次强杀重启恢复）；P41 自主 5.3h 并在 503 熔断后自动切模型自愈；P45 自动退回修复。**缺口**：合入仍需操作员或看门狗确认；尚缺带全套 11-19 修复的完整免救场大单闭环。 |
| **5. 产出质量更高** | ~85% | ~55% | 需求合同、产物快照、独立行为检查、完成时自动核对、交付门、异端审阅建议已落地；`core-v1` 36/36 零返工，P41/P45 跨端审阅多次抓出真缺陷。**缺口**：缺用户人工质量验收及与旧架构的同任务前后对照。 |
| **6. 同时降低用量消耗** | ~65% | ~15% | **目前最薄弱**：账目拆分、角色上下文选择、缓存 TTL/稳定前缀、检查复用已就绪（P41/P45 缓存读约 97%）。**缺口**：价格表与货币费用核算未实现；原生子代理仍有覆盖缺口；**无同任务同质量对照证明总用量/费用下降**。 |

**总体判断**：P0A–P5 工程骨架已全部并入 `main`（约 80%–85%），但阶段出口所需的**人工体验验收**与**协作/用量对照证明**尚未完成，因此按 `architecture-evolution.md §14` 规则，**尚无阶段正式关闭**。

## 7. 运维、实测与避坑备忘

1. **Cargo 构建与测试命令**：始终通过 Windows 包装脚本；开发检查用 `CARGO_TARGET_DIR=target/audit`，正式发布用默认 `target/release`：
   ```powershell
   $env:CARGO_TARGET_DIR='target/audit'
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/cargo.ps1 build --workspace
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/cargo.ps1 clippy --workspace --all-targets -- -D warnings
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/cargo.ps1 test --workspace --no-fail-fast -- --test-threads=2
   ```
2. **后台拉起 Windows GUI 桌面端**：发布版启用了 `#![windows_subsystem = "windows"]`。在自动化会话里直接运行 `super-agent.exe` 会立即返回并触发 Job Object 杀进程；需要用 `Start-Process ... -Wait` 放在常驻守护任务中持有进程，再通过 `scripts/agent-control.py --data <dir> status --ticket <id>` 核对 `scheduler.state == "running"`。
3. **长工单监守必须用本地静默看门狗**：禁止用短周期定时任务频繁唤醒 AI 会话（极度消耗主会话额度）。应写纯本地 Python 看门狗定时查 `agent-control.py` 与只读 SQLite，本地自动处理安全核查后的 `confirm`、偶发 `interrupted` 重试与 3.5h `follow` 提醒，**仅在工单结束、出现待处理提问/审批、候选异常、调度故障或低磁盘时退出唤醒会话**。
4. **模型路由与额度约束**：
   - 启动任何新工单前先核对实时目录与用户当前模型额度（Antigravity Neon 与 Codex `gpt-6.2-sol` 额度有限，勿未经确认盲开长时计费任务）。
   - 若继续用 `mc-genshin` 实测，**不要再把 Claude Opus 5.5 放在主控位**（在 P46 特效任务上连续两次读取项目后稳定触发模型侧拒答并叫停子任务；其留下的所有临时目录、停单记录及 CLI 历史残留已全部清除）。
   - 昨夜 Neon + GPT 6.2 sol 实测数据已只读归档于 `tmpstate/mcg-p46-neon/`（含 `patrol.py`、`spec.json` 与 `hub.sqlite3`），未含 Opus 污染。
5. **账本安全红线**：不要对用户真实工单库（`%USERPROFILE%\.local\share\superagent\control-room`）直接跑测试或双开调度器；测试一律用独立临时目录，旧库兼容测试一律用 SQLite backup 副本。
