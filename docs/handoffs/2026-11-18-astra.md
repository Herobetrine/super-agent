## 5. 下一轮建议优先做什么

以下是建议的下一开发包，不是已经实现的能力，也不要求新会话照搬未经核查的实现方案。

**优先补“实际行为检查与需求、输入版本、交付证据的绑定”，逐步完成 P1A。** 当前 SHA-256 标准只适合事先已知目标字节，不能普遍验证功能；直接跳到自适应调度，会缺少可信的质量反馈。

建议先研究现有项目完成检查及候选验证流程，复用命令运行、取消、检查结果和指纹机制。设计最小的行为证据类型及明确采用来源，避免另造一个调度器。重点解决：

1. 哪项需求由哪项操作员采用的检查验证，检查实际覆盖哪份输入、环境和命令版本。
2. 如何在冻结候选或可核验输入上运行；检查自身改文件、检查后改文件、需求同时修订、合入变化时，旧通过结果如何失效。
3. 验证结果怎样进入统一证据投影，缺失、失败和过期如何呈现；不能因为 agent 声称完成或自己改弱标准就通过。
4. 先完成明确范围的端到端回归，再决定是否接入自动交付；保留当前持续任务和有界修复语义。

人工接受记录应另行绑定精确交付版本，不能把文件标准通过冒充用户接受。自动需求提取、上下文选择、策略建议与调度、缓存及长期恢复按架构阶段逐步推进；本轮未做固定任务集质量/耗时/用量对照，因此没有证据宣称六项目标整体达成或固定节费比例。

## 7. 已修正的问题与仍须保持的约束

- 编辑器必须固定打开时的合同版本。刷新后旧草稿不能借新版本号绕过 CAS；冲突时保留草稿并禁用保存。
- 读侧验证实际对象和权威需求范围，不信任序列化的 pass/ready。当前未满足项不能沿用历史列表冒充新核验结果。
- 损坏的 assessment 字段、BLOB、非 UTF-8、超限及错误数值降为 invalid，不能让合法编辑在返回投影时回滚。
- 策略字段损坏则关闭门；版本号可信可追加恢复。版本号本身损坏则 `policy_revision=-1`，保持编辑可用，但策略需维护，不猜测版本高水位。
- Windows 对象原子替换前需关闭目标守护句柄；坏对象先隔离保留，不能先删除，也不能把权限/忙错误解释为可修复损坏。
- 当前对象读取有边界：每工单最多 256 需求，每次 128 文件，单文件 4 MiB、总计 64 MiB、清单 2 MiB；路径和重解析点限制见代码。不是整个仓库的原子时点快照，也没有对象回收器。
- 最近一次故障注入夹具最初被正常外键约束拒绝，后来仅在合成账本的独立连接模拟外部损坏。`core-before.log` 是从工具回执恢复的失败片段，原完整失败流被覆盖，不要声称完整原日志仍在。
